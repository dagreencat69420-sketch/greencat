## Bug 1 (fixed in scripts, no program change): crank dies on a transient RPC error

- **Evidence:** `crankA.log` at 08:02:25 PT "settled 6 NFT(s)", then at 08:02:34 an uncaught `TypeError: fetch failed … ConnectTimeoutError (api.devnet.solana.com:443)` and the Node process exited. The crank's loop has `try/catch`, so the error came from outside it.
- **Cause:** `@solana/web3.js` 1.99 `sendAndConfirmTransaction` → `getTransactionConfirmationPromise` starts an un-awaited `getSignatureStatus()` after the websocket subscription comes up. If the tx is already confirmed and that call later fails (429 / connect timeout), the rejection is unhandled and Node 20 exits. On launch day this would **silently stop the reveal safety net**.
- **Same root cause in `mint-nft.ts`:** RPC read errors in its auto-settle loop also had no retry; in phase D, 2 of 6 CLI mints exited with a stack trace before the reveal.
- **Fix (commit `78aad2d`):** `reveal.ts crank` logs and ignores unhandled rejections and timestamps loop errors; `mint-nft.ts` has the same guard and retries RPC reads. Verified in phases E/E2 (no aborts; crank survived a 429).
- The web app was not tested here (separate code path; it is a browser, not Node, so an unhandled rejection doesn't kill it).

## Design caveat (not a bug, needs an owner decision before mainnet)

On Devnet ORAO always answered, so a **real** oracle stall (a request that is never fulfilled) could not be produced. What the code does in that case (program `settle_mint` / `request_mint_vrf`; covered by localnet security tests GC-17 rereq/stale):

- Settles are strict FIFO, so if the **head** mint's request is never fulfilled, **every later mint stays a placeholder** until that request expires and anyone (the crank does it automatically) re-requests it with `request_mint_vrf`.
- Expiry = `Config.vrf_expiry_secs`, which was **86,400 s (24 h) on Devnet during the drill** (set to 3,600 s / 1 h later the same day at 09:19:59 PT, tx `sjg9cB3bvMffy74koBoZwgzvgiPGxVYmqZm4YVmUKMg83iSWZ41eXSyvcj5xYQdyXx7FRLjYr6Zr1YydrhqUqDJ`). So a stuck head could hold up reveals for up to a day, and after 256 pending mints new mints fail with `MintQueueFull`.
- Option: set `npm run admin -- vrf-expiry 3600` (the program minimum, 1 h) on mainnet. The same setting also controls when unfulfilled **wheel** spins can be refunded, so it changes both. Nothing was changed.

## Recommendations

1. Run the crank against a **dedicated RPC** (`RPC_URL=<Helius>`), not the public endpoint: the public Devnet RPC answered 429 dozens of times during this small drill.
2. Run the crank under a supervisor that restarts it (systemd / Railway service / `while true; do …; sleep 5; done`) as a second safety net.
3. ~~Decide the mainnet `vrf_expiry_secs`~~: **decided Oct 3, 2026 PT: 3600 s (1 h) on mainnet**, set by the admin wallet right after the handover (checklist Phase 6, 10:35). Also makes unanswered wheel spins refundable after 1 h.
